# Week 6 — Incident Dataset, Memory/Evaluation Split, ChromaDB Retrieval Memory

Turns Week 5's raw telemetry JSONL (`telemetry/data/*.jsonl`) into a labeled incident dataset,
splits it into a Memory set (available to the future RCA agent's RAG retrieval) and an Evaluation
set (held out, never indexed), and builds a local, persistent ChromaDB collection from the Memory
set only.

## Architecture

```
dataset-tools/
├── src/dataset_tools/
│   ├── config.py            paths, fault→service mapping, split seed/fraction, fault defaults
│   ├── ingest.py             reads telemetry/data/*.jsonl (never writes there - read-only)
│   ├── reconstruct.py        phase reconstruction (NORMAL/FAULT_INTRODUCTION/FAULT_ACTIVE/RECOVERY)
│   ├── incidents.py          incident assembly + description/summary/postmortem text generation
│   ├── synthetic_model.py    deterministic synthetic incident generator
│   ├── generate.py           drives additional real live experiments via telemetry.experiment
│   ├── build_dataset.py       orchestrates: real + synthetic -> IDs -> split -> manifest
│   └── chroma_store.py        ChromaDB build / query / leakage validation
├── tests/                    42 pytest tests (see "Testing" below)
├── data/
│   ├── processed/             all_incidents.jsonl, split_manifest.json (full dataset, both sets)
│   ├── memory/                 memory_incidents.jsonl (RAG-eligible)
│   └── evaluation/             evaluation_incidents.jsonl (held out, never indexed)
├── chroma/                    ChromaDB's own persistent storage (gitignored - rebuildable)
├── requirements.txt
└── pyproject.toml
```

`telemetry/data/` is treated as immutable: `ingest.py` only reads from it, nothing in
`dataset-tools` ever writes there.

## Incident record schema

Every incident (real or synthetic) is one JSON object with these fields:

`incident_id`, `experiment_id`, `data_source` (`"real"` or `"synthetic"`), `generation_method`
(`"live_experiment"` or `"deterministic_model"`), `fault_type`, `root_cause_service`,
`symptom_service`, `affected_services`, `start_time`, `end_time`, `phases` (NORMAL /
FAULT_INTRODUCTION / FAULT_ACTIVE / RECOVERY start/end timestamps), `baseline_metrics`,
`fault_metrics`, `recovery_metrics` (per-service averaged curated Prometheus metrics),
`metric_deltas` (fault − baseline, only where both sides have a real value), `payment_probe_summary`
(per-phase count/success_rate/avg_duration_ms/notification_status_counts), `errors_observed`,
`correlation_ids`, `fault_configuration`, `severity` (heuristic: `low`/`medium`/`high`/`unknown`),
`root_cause_description`, `symptom_description`, `summary`, `postmortem_text` (the field embedded
into ChromaDB). Synthetic incidents additionally carry `synthetic_parameters` (every random
parameter and seed used to generate them).

## Root cause vs. symptom service (empirically verified, not assumed)

| fault_type | root_cause_service | symptom_service | same service? |
|---|---|---|---|
| `memory-leak` | payment-service | payment-service | yes |
| `db-lock` | ledger-service | ledger-service | yes |
| `auth-key-error` | auth-service | **payment-service** | **no** |
| `notification-latency` | notification-service | **payment-service** | **no** |

`auth-key-error` and `notification-latency` are deliberately cross-service, mirroring
`CLAUDE.md`'s design intent that the RCA system must eventually identify a root cause on a
*different* service than the one exhibiting the symptom. This was confirmed by directly querying
real Week 5 telemetry (`telemetry/data/telemetry_2026-08-27.jsonl`): during an auth-key-error
fault window, `auth-service`'s own `http_server_requests_error_count` stays at `0.0` throughout
(its `/api/auth/validate` endpoint always returns HTTP 200, reporting validity in the response
body rather than the status code), while `payment-service`'s error count rises across the failed
probes — the HTTP-level failure is generated by payment-service's own exception handling in
response to the rejected token, not by auth-service itself.

## Phase reconstruction: a real bug found and fixed during this week

Each telemetry record's `fault.faultActive` field is that record's **own service's**
self-reported fault status (from its own `/fault-status` endpoint) — not a global "is the
experiment's fault active" flag. For the two single-service faults (memory-leak, db-lock) this
happens to be the right signal, because the root-cause service *is* the only service whose metrics
matter. But for the two cross-service faults, the symptom service (payment-service) never has a
fault of its own active, so its own `faultActive` is always `false` — and an earlier version of
`reconstruct.phase_label_telemetry` read that flag for every service's own records, which silently
mislabeled *all* of payment-service's fault-window telemetry as `FAULT_INTRODUCTION` instead of
`FAULT_ACTIVE`, dropping it out of `fault_metrics` entirely (all 4 real `auth-key-error` incidents
had `severity: "unknown"` and a missing `fault_metrics["payment-service"]` before the fix).

**Fix:** the self-reported `faultActive` flag is now only trusted for the record whose `service`
matches the experiment's actual injection target (`experiment["service"]`); every other service's
telemetry falls back to the same time-window rule already used for payment probes (the
injected→reset window is `FAULT_ACTIVE`, since fault injection/reset happen synchronously inside
the Java controller's `inject()`/`reset()` call). See `reconstruct.phase_label_telemetry`'s
docstring and `tests/test_reconstruct.py::test_phase_label_telemetry_symptom_service_not_mislabeled`
for the regression test.

A second bug was found in the same pass: `incidents.generate_descriptions`'s `postmortem_text`
used Python's string-literal-adjacency concatenation followed by a trailing `if/else` ternary —
because adjacent string literals bind *tighter* than a conditional expression, the ternary's
`else` branch (used whenever `root_cause_service == symptom_service`, i.e. memory-leak and
db-lock) evaluated to *only its own last line*, silently discarding the entire timeline/root-cause/
symptom/errors text that preceded it. Fixed by building the closing line separately and
interpolating it into the full f-string instead of splitting the ternary across the whole
concatenation. See `tests/test_incidents.py::test_build_incident_postmortem_text_contains_full_content_for_same_service_fault`.

## Real vs. synthetic data (explicitly labeled, never conflated)

**16 real incidents** (`data_source: "real"`, `generation_method: "live_experiment"`) — 4 per
fault type — reconstructed from actual live experiments run against the real Kubernetes
deployment via `telemetry.experiment.run_experiment()` (Week 5's own orchestrator, extended this
week with one optional `inject_body` parameter so `notification-latency`'s delay could be varied
per run). One experiment per fault type already existed from Week 5; `generate.py` drove 3
additional live experiments per fault type this week (12 total), each with a different
baseline/fault/recovery timing combination, so real incidents also vary in phase duration and
sample density, not just fault magnitude.

**52 synthetic incidents** (`data_source: "synthetic"`, `generation_method: "deterministic_model"`)
— 13 per fault type, generated by `synthetic_model.py` to bring every fault type up to the same
total (17) without needing 68 live experiments. Nothing here is arbitrary or fabricated
independent of the real system:

- Baseline JVM memory ranges (`OBSERVED_BASELINE_RANGES`) are anchored to values actually observed
  in the real experiments (e.g. ledger-service's baseline heap usage is consistently higher than
  the other three services — real, not invented — because of its JPA/Hibernate footprint).
- Each fault's fault-phase metric formula mirrors the *actual Java fault mechanism* it represents,
  cited by class/method name in `synthetic_model.py`'s comments:
  - `memory-leak`: `MemoryLeakFaultService.allocateIfEnabled()` — a fixed-size chunk retained
    every `interval_ms` while enabled, capped at the real `max_total_bytes` safety limit.
  - `db-lock`: `DbLockFaultService.inject()` — `connections_to_hold` connections acquired
    synchronously, always drawn from `{3, 5, 7, 9}` (strictly below the real `pool_size=10`, the
    same clamp the Java code itself enforces).
  - `notification-latency`: the real interaction between `NotificationController`'s configured
    sleep and payment-service's own ~5000ms client-side timeout — a `delay_ms > timeout_ms` draw
    produces a `FAILED` notification outcome, `delay_ms <= timeout_ms` produces `SENT`, exactly
    matching the real system's observed behavior.
  - `auth-key-error`: the empirically-confirmed cross-service pattern above (error surfaces on
    payment-service, not auth-service).
- Every synthetic incident's parameters and its exact seed are recorded in
  `synthetic_parameters`, and generation is fully deterministic:
  `generate_synthetic_incident(fault_type, index, base_seed, base_start)` always produces
  byte-identical output for the same four inputs.

Both `data_source` and `generation_method` are present on every incident record, so a reader (or
the future RCA agent) can always tell which incidents came from the live system and which were
generated, and neither is ever presented as the other.

## Memory/Evaluation split (enforced in code, not just documented)

- **Split:** deterministic, stratified by `fault_type`, seed `42`
  (`config.SPLIT_SEED`), memory fraction `20/68` (`config.MEMORY_FRACTION`).
  `split.stratified_split()` groups incidents by fault type, sorts each group by `incident_id`
  (so grouping order never depends on dict/file iteration order), derives a per-fault-type
  sub-seed as `random.Random(f"{seed}:{fault_type}")`, shuffles, and splits proportionally. Running
  the same input set through this function twice always produces byte-identical Memory/Evaluation
  assignment (see `tests/test_split.py::test_split_is_deterministic_across_repeated_runs`).
- **Result:** 20 Memory / 48 Evaluation, exactly 5 Memory + 12 Evaluation per fault type (all four
  fault types represented in both sets — CLAUDE.md's "reasonable coverage...in both sets").
- **Code-level enforcement, not convention:**
  1. `chroma_store.build_collection()` reads incidents to index **only** from
     `config.MEMORY_INCIDENTS_FILE` — `config.EVALUATION_INCIDENTS_FILE` is never opened by the
     indexing path at all.
  2. Before writing anything to the collection, it computes
     `memory_ids & evaluation_ids` (loaded read-only, for comparison only) and raises
     `EvaluationLeakageError` if the intersection is non-empty — so even a corrupted/hand-edited
     Memory file that happened to contain an Evaluation ID is rejected before any data is
     persisted, not just before returning "success".
  3. After building, it re-checks by directly querying the built collection for every Evaluation
     ID (`collection.get(ids=evaluation_ids)`) and raises if any come back.
  4. `chroma_store.validate_no_leakage()` is a standalone entry point that re-runs both checks
     against whatever collection already exists on disk, without rebuilding it — usable as an
     independent audit step.
  - Tests: `tests/test_chroma_store.py::test_build_collection_raises_if_evaluation_id_leaks_into_memory_file`,
    `test_split.py::test_no_incident_id_appears_in_both_sets`.

## ChromaDB

- **Local, persistent, no cloud dependency.** `chromadb.PersistentClient(path=dataset-tools/chroma/)`.
  Collection name: `incident_memory`.
- **Embedding:** ChromaDB's bundled default embedding function — a small local ONNX model
  (`all-MiniLM-L6-v2`, ~80MB), downloaded once from ChromaDB's own model bucket and cached at
  `~/.cache/chroma/onnx_models/` on first use. After that first download, all embedding runs
  fully locally with no further network calls — the same "simple local embedding, no cloud API"
  shape Week 7's Ollama-based RAG will need, so nothing here conflicts with that later work; the
  two are independent local-inference paths (ChromaDB's embedding model vs. Ollama's LLM) that
  can coexist without modification.
- **Contents:** the 20 Memory incidents only. Document text = `postmortem_text` (the full
  timeline/root-cause/symptom narrative). Metadata per record: `incident_id`, `fault_type`,
  `root_cause_service`, `symptom_service`, `severity`, `data_source`.
- **Tooling:** `python -m dataset_tools.chroma_store` (build, resets and rebuilds the collection),
  `python -m dataset_tools.chroma_store validate` (leakage check only, no rebuild),
  `python -m dataset_tools.chroma_store query "<text>"` (prints the top-3 similar Memory incidents
  as JSON).

### Example retrieval

```
$ python -m dataset_tools.chroma_store query "ledger service database connection pool exhausted, HikariCP connections held, transactions timing out"
inc-0020  db-lock        real       distance=0.484
inc-0029  db-lock        synthetic  distance=0.509
inc-0032  db-lock        synthetic  distance=0.511

$ python -m dataset_tools.chroma_store query "JWT token validation failing with 401 unauthorized errors after key rotation"
inc-0003  auth-key-error real       distance=0.858
inc-0001  auth-key-error real       distance=0.891
inc-0007  auth-key-error synthetic  distance=0.958
```

Every result across all four fault-type queries returned only Memory-set incident IDs, correctly
ranked by fault-type relevance.

## Building the dataset from scratch

```bash
cd dataset-tools
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt && pip install -e .

# 1. (optional) generate more real experiments - requires the 4 services reachable on
#    localhost:8081-8084 (native, Docker Compose, or `kubectl port-forward`) and all 4 faults
#    currently inactive (GET /fault-status on each).
python -c "from dataset_tools.generate import run_additional_real_experiments; run_additional_real_experiments(runs_per_fault=3)"

# 2. reconstruct real incidents + top up with synthetic + split
python -m dataset_tools.build_dataset

# 3. build the ChromaDB collection from the Memory set (first run downloads the ~80MB embedding
#    model once; every run after that is fully offline)
python -m dataset_tools.chroma_store

# 4. verify
python -m dataset_tools.chroma_store validate
python -m dataset_tools.chroma_store query "payment service returning errors after auth failure"
```

## Testing

```bash
cd dataset-tools && source .venv/bin/activate && python -m pytest tests/ -v
```

42 tests, covering: JSONL ingestion (7), event/telemetry joining (3), phase reconstruction (8,
including the two regression tests for the bugs above), incident construction (9), metric delta
calculations (1), fault labeling (2), deterministic dataset splitting (2), class/fault
distribution across splits (2), strict Memory/Evaluation separation (2), ChromaDB indexing only
Memory records (1), evaluation IDs rejected from indexing (1), retrieval returns valid Memory
incidents (2), handling incomplete/partial telemetry (2), handling unavailable
services/collection errors (2). None mock ChromaDB itself — they use a real local
`PersistentClient` against a pytest `tmp_path`, isolated per test via `monkeypatch` on
`config.MEMORY_INCIDENTS_FILE` / `EVALUATION_INCIDENTS_FILE` / `CHROMA_DIR` /
`CHROMA_COLLECTION_NAME`.

## Reproducibility

- Split seed (`42`) and memory fraction (`20/68`) are both named constants in `config.py`.
- Synthetic incident generation is a pure function of `(fault_type, index, base_seed, base_start)`
  — no wall-clock time or unseeded randomness anywhere in `synthetic_model.py`.
- `assign_incident_ids` sorts by `(fault_type, data_source, start_time)` before assigning
  sequential `inc-XXXX` IDs, so the same input incident set always yields the same ID assignment
  regardless of dict/list construction order upstream.
- Re-running `build_dataset.build()` against the same `telemetry/data/` contents always produces a
  byte-identical `all_incidents.jsonl`, `memory_incidents.jsonl`, `evaluation_incidents.jsonl`, and
  `split_manifest.json`.
